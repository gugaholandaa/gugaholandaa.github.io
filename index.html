01 / perfil

Onde estou hoje

Concluí a graduação na área de tecnologia e aprendi a programar principalmente por conta própria: documentação, videoaulas e projeto na tela. O percurso não foi linear — houve interrupções e retomadas. Hoje mantenho uma hora de estudo por dia, e o que me trouxe até aqui foi constância, não intensidade.

O que não vou omitir: nunca ocupei o cargo de desenvolvedor, não trabalhei em uma base de código compartilhada com outras pessoas e ainda levo horas no que um desenvolvedor experiente resolve em minutos. Prefiro declarar isso agora a descobrir junto com o time na terceira semana.

Sobre ferramentas: uso IA no meu processo de desenvolvimento, como boa parte do mercado hoje. O critério que aplico é único e inegociável: só considero pronto o que consigo explicar. Se não sei justificar por que uma linha está ali, ela ainda não é minha.

O que ofereço: constância, disposição para as tarefas que ninguém escolhe e receptividade a code review — refaço o que estiver errado e registro para não repetir. Para uma equipe disposta a investir algumas semanas em formação, isso se converte em entrega.

— lacunas declaradas

O que ainda não domino

Trabalho em equipe com Git (branch, pull request, resolução de conflito), testes automatizados e deploy em produção. E domínio integral do que já construí: faço funcionar, e estou fechando as lacunas de por que funciona.

— método

Como eu trabalho

Pergunto cedo em vez de travar por dias, registro o que aprendo para não perguntar duas vezes, e entrego em partes pequenas e testadas em vez de um bloco grande e instável.

projeto 01 · 2025 · entregue a cliente

Aduo Arquitetura — site institucional

O que é
Site institucional de um escritório de arquitetura e engenharia especializado em construção com EPS. Carrossel automático de projetos, menu hambúrguer no mobile, navbar fixa com resposta ao scroll, modal de contato, botão flutuante de WhatsApp e feed do Instagram integrado.
Contexto
Primeiro projeto com requisitos definidos por terceiros e prazo real. Ter alguém aguardando o resultado muda o método de trabalho: não há a opção de abandonar na metade quando a parte difícil aparece.
O que aprendi
Responsividade aplicada — testar no dispositivo, não apenas reduzir a janela do navegador. O sistema de grid do Bootstrap. E que acessibilidade não é acabamento: alt nas imagens e aria-label nos controles entraram neste projeto e permaneceram no meu padrão.
O que eu faria diferente hoje
Organizaria o CSS em blocos por seção em vez de um arquivo corrido, otimizaria o peso das imagens e reduziria o Bootstrap ao que de fato é usado. E manteria uma cópia publicada sob domínio próprio: o cliente encerrou os acessos e o site não está mais no ar — o código permanece no repositório.

projeto 02 · 2025

Incident Manager API

O que é
API REST que simula um fluxo de gestão de incidentes críticos: registrar um incidente, listar os abertos, atualizar o status conforme a ocorrência evolui e excluir. A documentação interativa é gerada automaticamente pelo Swagger, o que permite testar cada rota pelo navegador.
Contexto
Desenvolvi esta solução para automatizar a contagem manual de incidentes críticos que eu mesmo registrava em planilha. Foi a primeira vez que saí do front-end e precisei decidir onde os dados seriam armazenados e como voltariam a quem os solicitasse.
O que aprendi
Separação de responsabilidades em arquivos — main.py para as rotas, models.py para as tabelas, database.py para a conexão. A função de um ORM: escrever Python e deixar o SQLAlchemy traduzir para SQL. E por que uma API responde com códigos de status em vez de texto livre.
O que eu faria diferente hoje
Validaria a entrada e trataria exceções em vez de permitir a falha, e substituiria o SQLite por PostgreSQL para viabilizar produção.

projeto 03 · 2026 · em uso pelo cliente

Login Checker — verificação automatizada de acessos

O que é
Ferramenta de linha de comando que abre automaticamente uma lista de sistemas web, executa o login em cada um e gera um relatório HTML com o resultado de cada verificação. Suporta sete fluxos de autenticação diferentes — usuário e senha, e-mail com submit, código em dropdown, sistemas legados e checagem de disponibilidade sem login.
Contexto
Entregue como prestador de serviço a um cliente corporativo que precisava confirmar, todo dia, se os acessos de vários sistemas internos continuavam funcionando. A verificação era manual, um sistema por vez.
O que aprendi
Automação de navegador com Playwright. Separar configuração de código: a lista de sistemas vive em um arquivo YAML e o script não conhece nenhum site específico — para cobrir um novo sistema, ninguém precisa tocar no Python. E tratamento de credenciais: senha não entra em repositório, nem privado.
O que eu faria diferente hoje
Trocaria os sete tipos de login por classes de estratégia, para acrescentar um fluxo novo sem alterar o núcleo do script. E escreveria testes para o próprio verificador.
